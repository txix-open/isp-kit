# Технический дизайн: разбивка лог-файлов для VictoriaLogs (MSP-8839)

## 1. Постановка

ИС ПДП переводит сбор логов на VictoriaLogs,
в пайплайне VL один лог-файл не должен превышать **256 КБ**.

Требования к реализации:

- размер лог-файла — **218 КБ** (запас до 256 КБ);
- размер настраивается вручную в конфигурации (на случай, если не попадём в размер / лимит изменят);
- решение — на уровне либы (isp-kit логгер), размер настраивается через **локальную конфигурацию**
  вместе с остальными настройками `logfile` (решение из комментов к тикету);
- альтернатива «сервис-коллектор перед коллекторами VL» отклонена: дополнительная точка отказа
  и заметно большая сложность.

## 2. Текущее состояние

- Логгер — пакет `log` (адаптер zap). Файловый вывод — пакет `log/file`:
  собственный sink zap со схемой `lumberjack://` на базе
  [lumberjack v2.2.1](https://github.com/natefinch/lumberjack).
- lumberjack ротирует файлы **только целыми мегабайтами** (`MaxSize * 1 MiB`, поле `int`) —
  лимит 218 КБ выразить нельзя.
- Настройка через локальный конфиг (`config.yml`, секция `logfile`, читается в `bootstrap`):

  ```yaml
  logfile:
    path: /var/log/<module>/app.log
    maxSizeMb: 512   # дефолт 512
    maxBackups: 4    # дефолт 4
    compress: true   # дефолт true
  ```

  Ключи читаются как `LOGFILE.PATH`, `LOGFILE.MAXSIZEMB`, `LOGFILE.MAXBACKUPS`, `LOGFILE.COMPRESS`
  (через `config.Optional`, дефолты из `bootstrap`). `MaxDays` (возрастная чистка) зашит в 0.
- Ротация lumberjack: файл переименовывается в
  `<name>-2006-01-02T15-04-05.000<ext>` (UTC), создаётся новый; бэкапы хранятся по `maxBackups`,
  при `compress` сжимаются в `.gz`. Асинхронная чистка в отдельной горутине.
- Важное ограничение lumberjack: **запись длиннее лимита отклоняется с ошибкой** —
  в zap это приводит к потере лог-записи (ошибка уходит в `ErrorOutput` как `write error: ...`).

## 3. Цель

**Цель:** поддержка разбивки лог-файлов на части в килобайтах (байтово точный лимит части),
настраиваемой в локальном конфиге отдельным параметром `partSizeKb`.
Для сервисов, не задающих его, поведение не меняется.

## 4. Рассматриваемые варианты

| Вариант | Оценка |
|---|---|
| 1. lumberjack как есть (`maxSizeMb: 1`) | Не подходит: 1 МБ > лимита 256 КБ. Целые МБ — жёсткое ограничение API lumberjack. |
| 2. Сервис-коллектор перед VL-коллекторами (нарезка чанков) | Отклонён: доп. точка отказа, отдельный деплой, сложность выше пользы. |
| 3. **KB-ротация внутри `log/file`** (новый writer с байтовым лимитом + ключ в конфиге) | **Выбран**: минимальная площадь изменения, семантика 1-в-1 с текущей ротацией, опционально для остальных сервисов. |

## 5. Решение

### 5.1. Конфигурация

Добавляется **отдельная настройка именно для разбивки логов** — размер части (чанка)
`partSizeKb`, в секцию `logfile` локального конфига:

```yaml
logfile:
  path: /var/log/<module>/app.log
  partSizeKb: 218  # НОВОЕ: размер части при разбивке; дефолт 0 — разбивка выключена
  maxBackups: 4
  compress: false  # для ПДП см. §8
```

- Приоритет: **если заполнен `partSizeKb` — используем его** (лог разбивается на части
  по `partSizeKb`), `maxSizeMb` в этом случае не действует.
- `partSizeKb` не задан (0) → текущее поведение lumberjack по `maxSizeMb` (дефолт 512 МБ).
- Дефолт в ките — `0` (фича opt-in); сервисы ПДП ставят `218` в своём конфиге.
- Размер считается в байтах: `partSizeKb: 218` = 218 × 1024 = **223 232 байта** — запас
  до 256 КБ держится в обеих интерпретациях лимита VL (256 000 / 262 144 байта).
- Если в сервисе уже стоит `maxSizeMb` — убирать его не нужно: `partSizeKb` имеет
  приоритет, `maxSizeMb` просто не участвует.

### 5.2. Реализация в `log/file`

- Новый writer `rotatingFileWriter` (`io.WriteCloser`) — ротация по байтовому лимиту,
  семантика 1-в-1 с lumberjack (см. §6), плюс:
  - запись длиннее лимита **не отклоняется**: происходит ротация, затем строка пишется целиком
    в новый файл (файл может превысить лимит максимум на длину одной записи — без потери данных,
    в отличие от lumberjack, который такие записи теряет);
  - имя бэкапа при коллизии (две ротации в одну миллисекунду) получает числовой суффикс.
- `Output` расширяется полем `PartSizeKb int` (размер части при разбивке);
  `ConfigToUrl` / `fileOutputConfigFromUrl` переносят параметр `partSizeKb` в URL sink'а
  (обратная совместимость: параметр, отсутствующий в URL, парсится как 0 — старые вручную
  собранные `lumberjack://...` URL продолжают работать).
- `NewFileWriter(Output)` выбирает реализацию: `PartSizeKb > 0` → `rotatingFileWriter`
  (разбивка), иначе lumberjack. Остальной код кита sink'ом не интересуется.
- Отдельную схему sink'а не вводим: `lumberjack://` остаётся, выбор реализации
  происходит в фабрике sink'а по `partSizeKb` (регистр `zap.RegisterSink` не меняется,
  совместимость с существующими URL сохранена).

### 5.3. Интеграция в `bootstrap`

- Чтение `LOGFILE.PARTSIZEKB` с дефолтом `0` и передача в `file.Output`
  (рядом с существующими `LOGFILE.MAXSIZEMB` / `LOGFILE.MAXBACKUPS` / `LOGFILE.COMPRESS`).
- Структура `bootstrap.LogFile` дополняется полем `PartSizeKb` (документация структуры конфига).

### 5.4. Изменения

| Файл | Изменение |
|---|---|
| `log/file/rotating_writer.go` | Новый файл: writer с байтовой ротацией (ротация, имена бэкапов, retention, сжатие, асинхронная чистка) |
| `log/file/file_output.go` | `Output.PartSizeKb`; round-trip URL; выбор writer в `NewFileWriter` |
| `bootstrap/base_bootstrap.go` | Ключ `LOGFILE.PARTSIZEKB` (дефолт 0) |
| `bootstrap/local_config.go` | `LogFile.PartSizeKb` |

Релиз кита: минорная версия (1.75.0 → 1.76.0) — новая фича, ничего не ломается.

## 6. Поведение разбивки / байтовой ротации (детали)

Разбивка реализована как ротация файла: каждая часть (файл) не превышает `partSizeKb`.

Разбивка происходит **в момент записи**: часть — отдельный файл на диске,
промежуточных буферов нет. `maxSizeMb` в разбивке не участвует вовсе —
он действует только в сервисах без `partSizeKb` (старый режим ротации lumberjack).

- Ленивое открытие файла при первом `Write` (zap открывает sink при построении логгера,
  но файл создаётся лениво — как в lumberjack).
- При открытии: если существует файл и `size + запись > лимит` → ротация.
- При записи: если `size + запись > лимит` → ротация:
  1. закрыть файл;
  2. переименовать в `<name>-<timestamp UTC>.<ext>` (формат `2006-01-02T15-04-05.000`,
     тот же, что у lumberjack — бэкапы обоих writer'ов неперепутываемы в одной директории);
  3. создать новый файл с оригинальным именем (режим прав старого файла наследуется);
  4. запустить асинхронную чистку.
- Чистка (горутина, по каждой ротации; при частых ротациях запуски схлопываются —
  каждый проход сканирует все бэкапы, ничего не остаётся):
  - удалить старые бэкапы сверх `maxBackups` (0 — хранить все);
  - при `compress: true` — зажать в gzip не-сжатые бэкапы, удалить исходные.
- При перезапуске: старый файл больше лимита → первая запись сразу ротирует его;
  меньше лимита → дописываем в ту же часть, принудительной ротации нет.
- Мутовариант: все `Write` сериализуются мьютексом (предположение lumberjack:
  в файл пишет один процесс).
- При высокой частоте логов части ротируются каждые несколько секунд — ротация это
  `rename` + создание маленького файла, накладных расходов не замечается.
- `Close()` (zap зовёт при `Sync`; кит вызывает `Sync()` при закрытии приложения)
  закрывает файл; следующий `Write` открывает снова.
- Ограничение на размер файла — «мягкое по записи»: файл ≤ лимита + длина одной строки.

## 7. Тестирование

Юнит-тесты в `log/file` (`t.TempDir`, реальные файлы):

1. Ротация при превышении лимита: содержимое старого бэкапа и нового файла; порядок записей.
2. Дописывание в существующий файл без ротации, если лимит не превышен.
3. `maxBackups=N`: после серии ротаций на диске ровно N свежайших бэкапов.
4. `compress=true`: бэкапы становятся `.gz`, не-сжатые удаляются, gzip читается.
5. Одна запись длиннее лимита: не теряется, файл создан заново.
6. `Close()` (повторно) и `Write` после `Close`.
7. Одновременные `Write` из нескольких горутин (data race, целостность размера).
8. Round-trip `ConfigToUrl` → `fileOutputConfigFromUrl` с `partSizeKb`;
   URL без `partSizeKb` (совместимость) → 0.
9. Выбор реализации в `NewFileWriter`: KB → `rotatingFileWriter`, иначе lumberjack.
10. End-to-end через кит: `log.New(log.WithFileOutput(file.Output{PartSizeKb: ...}))` —
    запись через адаптер, проверка ротации и целостности содержимого частей.

Проверка в контуре ПДП (rollout): фактический размер файлов ≤ 218 КБ, VL получает записи.

## 8. Rollout (ПДП)

0. Предусловие: подтвердить с командой VL поведение коллектора по rotated-частям
   (§9.2) — от этого зависят `maxBackups`/`compress` в конфиге ПДП.
1. Выпустить новую версию кита (фича за конфигурацией — риск для остальных сервисов ~0).
2. В сервисах ПДП обновить isp-kit до 1.76.0 и в локальных конфигах добавить `partSizeKb: 218`.
   - `compress: false` — если VL-коллектор читает только обычные `.log`
     (с `.gz` не работает) — **нужно проверить** (см. §9).
3. Проверить: размеры файлов, поступление логов в VL, корректность хвоста при ротации.
4. Корректировка размера — только конфигурацией:
   - не попали в размер → поправить `partSizeKb`;
   - если VL поднимут лимит до ≥ 1 МБ → `maxSizeMb: 1` (существующий ключ, код не менять).

## 9. Риски и открытые вопросы

1. **218 КБ — маленький файл.** Читаемость деградирует: в VL операции разбиваются по «кускам»,
   склеивать последовательность VL не умеет — это делает оператор.
   Позиция по тикету: с таким ограничением глубокое расследование инцидентов мы брать на себя
   не будем; если VL смогут протюнить лимит хотя бы до 1 МБ — переключимся на `maxSizeMb: 1`
   конфигурацией. Ответа от VL пока нет.
2. **Поведение VL-коллектора с rotated-файлами** — ключевой вопрос к команде VL:
   коллектор собирает переименованные бэкапы (сканирует директорию) или только tail'ит
   текущий файл по имени? Если только текущий — при ротации фрагменты могут не попасть в VL.
   От этого зависят `maxBackups` и `compress` в конфиге ПДП и темп роста диска
   (при большом `maxBackups` / `0` части накапливаются).
3. **Записи длиннее 218 КБ** (крупные payload'ы в логах, debug): часть превысит
   `partSizeKb`, а вместе с записью — и 256 КБ. Если VL *отклоняет* файлы выше лимита
   (а не принимает), вся часть с этой записью может не попасть в VL — вместе с
   корректными строками. Вопрос к VL: oversized-файл отклоняется целиком? Варианты:
   принять как есть / запретить крупные payload'ы в file-лог для ПДП.
4. `partSizeKb` vs `maxSizeMb` заданы одновременно — действует `partSizeKb`.
   Валидацию «оба ключа» не делаем (избыточно для локального конфига);
   некорректное/отрицательное `partSizeKb` трактуется как 0 (режим lumberjack).

## 10. Принятые решения

| Дата | Решение |
|---|---|
| 02.11.2026 | Дефолт `partSizeKb` в bootstrap — `0` (opt-in; сервисы ПДП задают `218` в своём конфиге). Глобальный дефолт 218 КБ не вводим: isp-kit общий, изменение затронуло бы все сервисы. |
| 02.11.2026 | Сжатие rotated-файлов — без special case, семантика как у lumberjack; ПДП сам выбирает `compress` в конфиге. |
| 09.11.2026 | Настройка называется `partSizeKb` (размер части/чанка лога) — отдельная настройка именно для разбивки, а не альтернатива `maxSizeMb`; если заполнен — используется он. |
